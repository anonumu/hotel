# Архитектура и техническое описание реализации бэкенда (Java / Spring Boot)

## Информационная система управления гостиничным комплексом «Grand Impérial» (Hotel PMS)

Данный документ содержит полное архитектурное и техническое описание серверной части программного комплекса, разработанного на языке Java с использованием платформы Spring Boot. В документе описаны архитектурные слои, модель данных, жизненный цикл обработки запросов, конфигурация безопасности и обоснование ключевых инженерных решений.

---

## 1. Назначение системы и технологический стек

Программный комплекс представляет собой систему управления номерным фондом и бизнес-процессами гостиничного предприятия (**Property Management System, PMS**). Система обеспечивает учет номерного фонда, оформление и контроль бронирований, регистрацию и размещение постояльцев (Check-In / Check-Out), учет рабочего времени персонала, прием платежей, формирование счетов-квитанций и аналитику загрузки.

### Основные технологии и библиотеки:

* **Язык программирования:** Java 17 / Java 21 (LTS).
* **Фреймворк:** Spring Boot 2.7.18.
* **Сетевой и веб-слой:** Spring Web (RESTful API, JSON-сериализация через FasterXML Jackson).
* **Слой персистентности:** Spring Data JPA / Hibernate Core 5.6 (ORM).
* **СУБД:**
  * **H2 Database** (встроенная in-memory реляционная база данных для локальной разработки и тестирования, файл `hoteldb.mv.db`).
  * **PostgreSQL** (поддержка промышленной СУБД через профиль `application-postgres.properties`).
* **Безопасность:** Spring Security 5.7 (HTTP Basic, ролевая модель, фильтрация CORS, защита от перегрузок).
* **Валидация:** Hibernate Validator / Jakarta Bean Validation (`@Valid`, `@NotNull`, `@Min`, `@Max`).
* **Сборка и управление зависимостями:** Apache Maven 3.8+.

## 2. Архитектура приложения (Трёхслойная модель)

Серверная часть спроектирована по классической трёхслойной архитектуре (**3-Tier Layered Architecture**), обеспечивающей разделение ответственности (Separation of Concerns), слабую связанность компонентов (Loose Coupling) и высокую тестируемость кода:

```
  HTTP-клиент (Веб-интерфейс / Внешняя система)
                       │
                       │ JSON-запросы (GET, POST, PUT, DELETE)
                       ▼
┌─────────────────────────────────────────────────────────────┐
│ 1. Слой контроллеров (Web / Controller Layer)               │
│    Пакет: com.hotel.controller                              │
│    Классы: @RestController                                  │
│    Функция: маршрутизация URL, валидация DTO, возврат JSON  │
└──────────────────────────┬──────────────────────────────────┘
                           │ Вызовы методов сервисов
                           ▼
┌─────────────────────────────────────────────────────────────┐
│ 2. Сервисный слой (Service / Business Logic Layer)          │
│    Пакет: com.hotel.service                                 │
│    Классы: @Service                                         │
│    Функция: правила отеля, расчет цен, проверка пересечений │
└──────────────────────────┬──────────────────────────────────┘
                           │ Обращение к репозиториям
                           ▼
┌─────────────────────────────────────────────────────────────┐
│ 3. Слой доступа к данным (Data Access / Repository Layer)   │
│    Пакет: com.hotel.repository                              │
│    Интерфейсы: @Repository (JpaRepository<T, ID>)          │
│    Функция: генерация SQL через Hibernate, JPQL-запросы    │
└──────────────────────────┬──────────────────────────────────┘
                           │ SQL (JDBC)
                           ▼
┌─────────────────────────────────────────────────────────────┐
│ 4. База данных (Database Engine)                            │
│    H2 Database (In-Memory / File) или PostgreSQL            │
│    Таблицы: rooms, bookings, guests, staff, payments        │
└─────────────────────────────────────────────────────────────┘
```

### Назначение каждого слоя:

1. **Слой веб-контроллеров (`com.hotel.controller`):**
   * Точки входа для внешних HTTP-запросов.
   * Контроллеры не содержат сложной логики расчётов или прямых обращений к SQL. Их задача — принять входные данные, запустить валидацию переданного DTO, вызвать соответствующий метод сервиса и сформировать ответ `ResponseEntity` с нужным кодом статуса HTTP (`200 OK`, `201 Created`, `400 Bad Request`, `404 Not Found`).

2. **Сервисный слой бизнес-логики (`com.hotel.service`):**
   * Содержит все предметные правила работы гостиницы:
     * Проверка корректности периодов (дата выезда строго позже даты заезда).
     * Проверка вместимости номеров (число гостей не превышает лимит номера).
     * Контроль статусов номеров (нельзя забронировать номер в статусе ремонта `OUT_OF_ORDER`).
     * Алгоритм выявления наложений периодов бронирования одного и того же номера.
     * Расчет итоговой стоимости: `Количество_суток * Тариф_за_сутки`.

3. **Слой доступа к данным (`com.hotel.repository`):**
   * Содержит интерфейсы, расширяющие `JpaRepository<Entity, Long>`.
   * Реализация методов `findAll()`, `findById()`, `save()`, `deleteById()` генерируется библиотекой Spring Data JPA автоматически во время выполнения (на основе рефлексии и JPA Criteria/JPQL).
   * Для нетривиальных выборок используются декларативные JPQL-запросы (например, `findOverlappingBookings`).

4. **Сущности предметной области (`com.hotel.model`):**
   * Java-классы с аннотациями `@Entity` и `@Table`, отображаемые на таблицы реляционной базы данных.

5. **Объекты передачи данных (`com.hotel.dto`):**
   * Независимые структуры данных (DTO), применяемые в контрактах REST API. Исключают прямую передачу сущностей БД в клиентский слой, предотвращая утечку внутренних полей и атаки типа Mass Assignment.

## 3. Модель данных и управление персистентностью

### Конфигурация Hibernate и автогенерация схемы
В конфигурационном файле `application.properties` установлен режим:
```properties
spring.jpa.hibernate.ddl-auto=update
```
При запуске приложения Hibernate анализирует метаданные классов `@Entity` и автоматически создает или актуализирует структуру таблиц, первичных и внешних ключей без необходимости ручного написания DDL-скриптов.

### Встроенная СУБД H2
* **JDBC URL:** `jdbc:h2:mem:hoteldb` (in-memory) с сохранением в локальный файл `hoteldb.mv.db`.
* **Веб-консоль управления:** встроенная консоль администрирования доступна по адресу `http://localhost:8080/h2-console` (Пользователь: `sa`, пароль: пустой). Консоль позволяет инспектировать таблицы, индексы и выполнять произвольные SQL-выражения.

### Переключение на PostgreSQL
Проект поддерживает прозрачную смену СУБД без изменения исходного кода. В файле `src/main/resources/application-postgres.properties` сконфигурирован диалект PostgreSQL:
```properties
spring.datasource.url=jdbc:postgresql://localhost:5432/hotel_db
spring.datasource.driver-class-name=org.postgresql.Driver
spring.jpa.properties.hibernate.dialect=org.hibernate.dialect.PostgreSQL10Dialect
```
Активация осуществляется передачей параметра командной строки `--spring.profiles.active=postgres`.

## 5. Сквозной сценарий обработки запроса (End-to-End)

Для иллюстрации взаимодействия слоев рассмотрим сценарий создания бронирования номера:

1. **Клиентский уровень:**  
   Пользователь заполняет форму бронирования в веб-интерфейсе. Браузер отправляет HTTP-запрос методом `POST` на адрес `/api/v1/bookings` с телом:
   ```json
   {
     "roomId": 1,
     "guestId": 2,
     "checkInDate": "2026-11-20",
     "checkOutDate": "2026-11-25",
     "guestCount": 2
   }
   ```
2. **Уровень сетевой фильтрации (`MutationRateLimitFilter`):**  
   Запрос перехватывается серверным фильтром. Фильтр проверяет интенсивность мутирующих запросов (не более 35 операций в скользящем окне 2 секунды) для защиты от DoS-атак и флуда. При нормальной нагрузке управление передается цепочке фильтров Spring Security.
3. **Уровень контроллера (`BookingController`):**  
   Метод `createBooking(@RequestBody @Valid BookingRequestDto dto)` десериализует JSON в DTO-объект, проверяет базовые аннотации валидации и делегирует обработку сервису: `bookingService.createBooking(dto)`.
4. **Уровень бизнес-логики (`BookingService`):**  
   * Выполняется метод `validateDates(checkIn, checkOut)`: проверяется, что дата заезда не позже даты выезда и не находится в прошлом.
   * Выполняется валидация лимита гостей: `guestCount` находится в диапазоне 1–10.
   * Извлекаются сущности `Room` и `Guest` через соответствующие репозитории с проверкой их существования (при отсутствии выбрасывается `ResourceNotFoundException`).
   * Проверяется статус номера: если номер на ремонте (`RoomStatus.OUT_OF_ORDER`), создание брони блокируется с выбросом `BusinessLogicException`.
   * Выполняется запрос к БД `bookingRepository.findOverlappingBookings(...)` для исключения пересечения с уже существующими бронями.
   * Рассчитывается количество ночей проживания и общая сумма: `ночи * room.getPricePerNight()`.
   * Формируется сущность `Booking` со статусом `CONFIRMED`.
   * Вызывается метод сохранения `bookingRepository.save(booking)`.
5. **Уровень персистентности (Hibernate / H2):**  
   ORM Hibernate формирует параметризованный SQL-запрос `INSERT INTO bookings (...) VALUES (...)` и выполняет его через JDBC-драйвер в базе данных H2.
6. **Формирование ответа:**  
   Контроллер упаковывает сохраненную сущность в объект `ResponseEntity` со статусом `201 Created` и возвращает клиенту JSON-представление созданной брони.

## 7. Подсистема безопасности и отказоустойчивости

В проекте реализован многоуровневый подход к обеспечению надежности и безопасности:

1. **Защита от SQL-инъекций на уровне ORM:**  
   Все операции доступа к базе данных выполняются через интерфейсы Spring Data JPA и Hibernate. Внутри фреймворка используются исключительно параметризованные запросы (`PreparedStatement`). Параметры передаются отдельно от текста SQL-выражения, что делает внедрение стороннего исполняемого SQL-кода технически невозможным.

2. **Санитизация входных данных (`SecuritySanitizer`):**  
   Для текстовых полей реализован вспомогательный санитайзер, сканирующий строки на предмет потенциально опасных сигнатур: тегов `<script>`, обработчиков событий `onload=`, `onerror=`, псевдопротоколов `javascript:` и ключевых конструкций SQL-атак. При выявлении таких последовательностей операция прерывается с генерацией контролируемого исключения.

3. **Ограничение частоты запросов (`MutationRateLimitFilter`):**  
   Для предотвращения исчерпания пула соединений HikariCP и защиты базы данных от скриптового флуда запросами на изменение данных (POST, PUT, DELETE) реализован сервлетный фильтр `OncePerRequestFilter`. При превышении лимита 35 мутирующих операций за 2 секунды клиенту возвращается HTTP-код `429 Too Many Requests`.

4. **Глобальный обработчик исключений (`GlobalExceptionHandler`):**  
   Исключения приложения не приводят к отображению стандартных страниц трассировки Tomcat. Класс с аннотацией `@RestControllerAdvice` преобразует любые ошибки в предсказуемую JSON-структуру `ErrorResponseDto` с кодом статуса, кратким описанием причины и машиночитаемым кодом ошибки.

5. **Безопасность Spring Security (`SecurityConfig`):**  
   Настроен `SecurityFilterChain`. Публичные веб-ресурсы и REST API для клиентского интерфейса разрешены через `permitAll()`, а для административного доступа сконфигурирован встроенный менеджер пользователей `InMemoryUserDetailsManager` с ролями `ADMIN`, `MANAGER` и `RECEPTIONIST`.

## 8. Обоснование ключевых архитектурных и инженерных решений

В данном разделе систематизированы технические обоснования ключевых решений, принятых при проектировании серверной части комплекса.

### 8.1. Выбор Spring Boot вместо классического Servlet API
Классический подход на базе сервлетов (`HttpServlet`) и ручного JDBC требует значительного объема шаблонного кода для управления транзакциями, разбора HTTP-заголовков, сериализации JSON и настройки пулов соединений. Платформа Spring Boot предоставляет готовую экосистему с встроенным контейнером сервлетов (Tomcat), автоматической декларативной сериализацией данных через Jackson и декларативным управлением транзакциями, что многократно повышает надежность системы и снижает вероятность ошибок при работе с ресурсами.

### 8.2. Реализация принципов IoC и Dependency Injection
Для связывания слоев используется механизм **Constructor-based Dependency Injection** (внедрение зависимостей через конструктор). Контроллеры не инстанциируют сервисы через оператор `new`, а получают готовые экземпляры бинов от контейнера Spring. Это обеспечивает соблюдение принципа инверсии зависимостей (Dependency Inversion Principle из SOLID), изолирует компоненты и позволяет легко подменять зависимости mock-объектами при модульном тестировании.

### 8.3. Разделение `@RestController` и `@Controller`
Аннотация `@Controller` в традиционном MVC ориентирована на генерацию HTML-страниц на стороне сервера через шаблонизаторы. В данном проекте используется архитектурный паттерн **SPA (Single Page Application)**: сервер выполняет роль поставщика данных (API Gateway / Backend), а клиентский интерфейс работает на стороне браузера. Аннотация `@RestController` автоматически применяет `@ResponseBody` ко всем методам, возвращая типизированные JSON-структуры.

### 8.4. Использование DTO вместо прямых сущностей JPA
Передача сущностей `@Entity` напрямую в HTTP-запросы создает уязвимость **Mass Assignment** (злоумышленник может передать в JSON системное поле `id` или статус бронирования и перезаписать его). Использование независимых классов `BookingRequestDto`, `GuestRequestDto` жестко регламентирует состав полей, принимаемых от клиента, и позволяет применять к ним аннотации валидации Jakarta Bean Validation (`@NotNull`, `@Size`, `@Min`).

### 8.5. Алгоритм выявления наложений бронирований
Для исключения проблемы «овербукинга» (одновременное бронирование одного номера двумя постояльцами) в `BookingRepository` реализован запрос с проверкой пересечения отрезков дат:
```sql
b.checkInDate < :checkOutDate AND b.checkOutDate > :checkInDate
```
Если в БД уже зафиксирована подтвержденная бронь, пересекающаяся с запрашиваемым интервалом, операция отклоняется на уровне сервиса до изменения состояния номера.

### 8.6. Управление транзакциями (`@Transactional`)
Методы сервисов, изменяющие состояние нескольких связанных сущностей (например, создание брони, пересчет статуса номера и начисление стоимости), помечены аннотацией `@Transactional`. Это гарантирует соблюдение принципов **ACID**: если в ходе операции возникнет сбой, все изменения будут автоматически откатаны (Rollback), что предотвращает появление некорректных или частично сохраненных данных в БД.

### 8.7. Конфигурация CORS (Cross-Origin Resource Sharing)
В классе `CorsConfig` реализован интерфейс `WebMvcConfigurer` с явным разрешением методов `GET`, `POST`, `PUT`, `DELETE` и заголовков `Authorization`, `Content-Type`. Это позволяет клиентскому веб-интерфейсу взаимодействовать с сервером как при совместном хостинге на порту 8080, так и в сценарии распределенного развертывания фронтенда на отдельном домене или порту.

### 8.8. Стратегия маппинга перечислений (`@Enumerated(EnumType.STRING)`)
По умолчанию JPA сохраняет значения перечислений Java в виде порядкового номера (`ORDINAL`, 0, 1, 2...). При добавлении новой константы в середину enum порядок индексов смещается, что приводит к искажению исторических данных в базе. Использование `EnumType.STRING` фиксирует строковое представление статусов (`AVAILABLE`, `OCCUPIED`), обеспечивая обратную совместимость и читаемость базы при прямом аудите через SQL.

### 8.9. Агрегация отчетности в `ReportService`
Аналитические методы контроллера `ReportController` агрегируют показатели в режиме реального времени:
* Загрузка номерного фонда рассчитывается как процентное отношение номеров в статусе `OCCUPIED` к общему размеру фонда.
* Выручка группируется по способам оплаты (`CARD`, `CASH`, `TRANSFER`) на основе записей таблицы `Payment`.
Такой подход не требует дублирования предрассчитанных итогов в БД и гарантирует актуальность аналитики.
